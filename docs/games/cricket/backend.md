# Cricket betting — backend

All routes live in `services/core-api-service/src/plugins/betting.ts` (shared with Matka/Lottery — see `docs/backend-services/core-api-service/backend.md` for the file-level index). Settlement math lives in `services/core-api-service/src/helpers/cricket.ts`. Player routes require `app.authenticate`; every `/internal/*` route requires `x-internal-key === INTERNAL_SERVICE_KEY` via a locally-defined `internal` hook (`betting.ts:13-16`) — the same env var admin-service's `callBetting()` helper sends. Admin-service's `BETTING_URL` (`services/admin-service/src/index.ts`, and its checked-in `.env`) used to point at port 3012, a pre-consolidation `betting-service` port nothing listens on — `core-api-service` actually runs on port 3001 (`ecosystem.config.js:32`) — breaking every admin-panel cricket write action (match/market/session create, settlement, fantasy player/league create, fantasy settlement, all three CricAPI sync buttons); fixed 2026-07-28. The two genuinely-nonexistent routes described below (`sync-series`/`import-series-matches`) remain broken independent of that fix — see `docs/Bugs/cricket-admin-series-import-routes-missing.md`.

## Match-winner / prop markets

- **`GET /cricket/matches`** (`betting.ts:139-147`) — matches with `status IN ('upcoming','live')`, each with its `open` markets nested (an N+1 query loop, one `SELECT` per match — fine at current admin-driven data volumes, would not scale to hundreds of concurrent matches).
- **`POST /cricket/bet`** (`betting.ts:149-164`) — validates `market_id`/`option_key`/`amount` via Zod, requires the market to be `open` and the parent match not `settled`/`closed`, looks up `option.odds` from the market's JSONB `options` array, computes `potential = round(amount * odds, 2)`, debits the stake (idempotency key `cricket_stake_<betId>`), then inserts the bet row. **No rollback if the insert fails after a successful debit** — same class of gap already noted for Matka in `docs/backend-services/core-api-service/backend.md`, but here there's genuinely no unique constraint the insert could violate (unlike Lottery's ticket-number race), so it's theoretical rather than observed.
- **`GET /cricket/my-bets`** (`betting.ts:166-169`) — last 100 bets, joined with match/market names.
- **`GET /cricket/matches/:id/live`** (`betting.ts:261-271`) — returns the match row (including the free-form `live_score` JSONB), all markets regardless of status, all sessions, and `cricket_match_players` joined to `cricket_fantasy_players` (used for the mobile "Live Fantasy Points" list — see caveat below).
- **`settleCricketMarket()`** (`helpers/cricket.ts:4-46`, internal route `/internal/cricket/settle`) — row-locks the market, marks it `settled`, and for every still-`pending` bet on it: if `resultKey` is `null` the market is voided (refund the stake, `payout = amount`); otherwise bets whose `option_key === resultKey` are marked `won` with `payout = potential_payout`, everything else `lost`. Credits are applied **after** the transaction commits, via a plain sequential `for` loop awaiting `creditPrize()` one bet at a time (not `Promise.all`, unlike the fantasy settlement path) — **the boolean `creditPrize()` returns is never checked** (`helpers/cricket.ts:43`), so a wallet-service outage or a rejected credit call during settlement silently fails to pay a winner while their bet is already durably marked `won` in Postgres. There is no retry job or reconciliation sweep anywhere in this codebase for that state — an operator would have to notice a support complaint and manually re-credit. This is the same fire-and-forget pattern already documented for Matka/Lottery settlement in `docs/backend-services/core-api-service/backend.md`, just confirmed to apply identically here.

## Session ("fancy") bets

- **`POST /cricket/session/bet`** (`betting.ts:273-287`) — requires the session `open` and match not `settled`/`closed`, picks `odds_yes`/`odds_no` by `selection`, stores the *opposite* bracket edge as `bracket` for display (`selection === 'yes' ? session.max_runs : session.min_runs`), debits (idempotency `cricket_session_stake_<betId>`), inserts.
- **`settleCricketSession()`** (`helpers/cricket.ts:129-174`, internal `/internal/cricket/session/settle`) — `resultRuns === null` voids and refunds every pending bet; otherwise a `yes` bet wins if `resultRuns >= bet.runs_bracket`, a `no` bet wins if `resultRuns < bet.runs_bracket`. Same "credit result never checked" gap as market settlement (`helpers/cricket.ts:170-172`).
- **No `GET /cricket/session/my-bets` route exists**: the mobile History tab calls `GET /api/betting/cricket/session/my-bets` (`mobile/lib/features/games/betting/cricket_page.dart:2484`), but grepping `betting.ts` for `session/my-bets` returns nothing — there is no route registered under that path anywhere in the file. This was previously filed generically as `docs/Bugs/betting-mobile-routes-missing-on-backend.md`; this pass reconfirms it's still missing and the mobile History tab (`docs/games/cricket/mobile.md`) silently shows "No session bets yet" as a result, indistinguishable from a user with genuinely zero bets.

## Fantasy cricket

- **`GET /cricket/players`** (`betting.ts:171-182`) — all fantasy players, or filtered to the two teams of a given match.
- **`POST /cricket/fantasy/team`** (`betting.ts:184-208`) — validates exactly 11 distinct player UUIDs, captain ≠ vice-captain, both are members of the roster, match still `upcoming`, then enforces: **budget cap `totalCredits > 100.0` rejected** (`betting.ts:201`), 1–4 wicket-keepers, 3–6 batsmen, 1–4 all-rounders, 3–6 bowlers. **There is no server-side check on how many of the 11 come from a single team** — the mobile client enforces "max 7 per team" purely client-side (see `docs/games/cricket/mobile.md`); a direct API call (or a future client) could submit an 11-player roster entirely from one team. See `docs/Bugs/cricket-fantasy-roster-validation-mismatch.md` for this plus the budget-cap number mismatch below.
- **`POST /cricket/fantasy/join`** (`betting.ts:222-259`) — league must be `open` and under `max_entries`, team must belong to the caller and match the league's match, one entry per user per league (`UNIQUE (league_id, user_id)` in `infra/db/migrations/010_cricket_fantasy_and_live.sql:77`, pre-checked at `betting.ts:234`). Debits the entry fee **before** re-checking capacity inside a transaction with `FOR UPDATE` (`betting.ts:242`) — if the race-recheck finds the league just filled/closed, it rolls back and issues a refund via `creditPrize()` (`betting.ts:246`), but that refund call's result is also unchecked and, unlike market/session settlement, **no entry row is ever inserted in this failure path** — if the refund silently fails (wallet-service down at that exact moment), there is zero database trace that the user was charged, making this specific race harder to reconcile than the settlement-credit gaps above. This is a narrow double-failure window (concurrent last-slot joins *and* a wallet-service hiccup) so it's noted here rather than filed as a standalone bug, but it's worth knowing this path has no reconciliation trail at all.
- **`settleFantasyLeague()`** (`helpers/cricket.ts:48-127`, internal `/internal/cricket/fantasy/settle`) — this single function does three things atomically in one transaction: (1) upserts `cricket_match_players.fantasy_points` from an admin-supplied `{ playerId: points }` map, (2) recomputes every submitted team's `points_total` (captain ×2.0, vice-captain ×1.5, else ×1.0) and copies that onto every `cricket_fantasy_entries.points` for that match, (3) for every still-`open` league on the match: ranks entries by points (ties share the lower rank via a running "if lower than previous, advance to current index" scan, `helpers/cricket.ts:92-95`), looks up each rank's payout tier from the league's `prize_distribution` JSONB, and **marks every league `settled` and the whole match `settled`** (`helpers/cricket.ts:114,117`) before committing. Payouts are then credited via `Promise.all()` (unlike the sequential loop in market/session settlement) — a faster but equally unchecked fire-and-forget (`helpers/cricket.ts:109-112`).
  - **Consequence**: there is no way to post an interim, non-final fantasy scorecard update. The *only* code path that ever writes `cricket_match_players.fantasy_points` is this one, and calling it always immediately settles every open league on the match and marks the match itself `settled`. See `docs/Bugs/cricket-live-fantasy-points-never-update.md` — the mobile live-match screen displays a "Live Fantasy Points" section captioned "updates every ~2 min" that in fact never updates until the match (and every contest on it) is over.
- **Missing routes the mobile client calls**: `GET /cricket/fantasy/leagues/:id/leaderboard` (used by the contest leaderboard screen) and `GET /cricket/fantasy/team/:teamId` (view a specific submitted team) — neither exists in `betting.ts`. Both fail silently client-side. Already covered generically by `docs/Bugs/betting-mobile-routes-missing-on-backend.md`; this pass adds that the **My Contests tab never even reaches the point of calling the leaderboard route for most users**, because of a separate field-name bug — see `docs/Bugs/cricket-my-contests-tab-joined-field-mismatch.md` below.
- **`GET /cricket/fantasy/leagues`** (`betting.ts:216-220`) returns each league with a computed `joined_entry_id` column (`(SELECT id FROM cricket_fantasy_entries WHERE league_id = l.id AND user_id = $2)`, null if the caller hasn't joined) — **it never returns a field called `joined_count`**. The mobile client reads `league['joined_count']` in three places to decide whether the user has already joined a contest. Since that key is always absent, `?? 0` makes it permanently `0`, so the app can never tell it's already joined a league it in fact has. Full detail and impact: `docs/Bugs/cricket-my-contests-tab-joined-field-mismatch.md`.

## Admin-only match/market/session CRUD

`POST /internal/cricket/match`, `/internal/cricket/market`, `/internal/cricket/fantasy/players`, `/internal/cricket/fantasy/leagues`, `/internal/cricket/session/create`, `/internal/cricket/scores/update` (`betting.ts:327-373`) are all thin Zod-validated inserts/updates, no settlement logic — see `docs/games/cricket/admin.md` for the admin-panel forms that drive them. `/internal/cricket/scores/update` (`betting.ts:351-361`) builds its `UPDATE` dynamically field-by-field (only touches `live_score`/`live_tv_url`/`status` if present in the body) — reasonable partial-update behavior, no COALESCE footgun here since it explicitly skips absent fields rather than writing them as NULL.

## CricAPI sync routes — the fallback key and what it actually does

`/internal/cricket/sync-api`, `/internal/cricket/sync-countries`, `/internal/cricket/sync-squad` (`betting.ts:388-457`) are synchronous pass-throughs to `https://api.cricapi.com/v1/*`, keyed by `game_configs.special_rules.api_key` for the `cricket` row if set, else a hardcoded literal (`dd511ce4-aeb7-4e1f-86f4-1160404b2776`, three times: `betting.ts:391,420,436`) — filed as `docs/Bugs/hardcoded-cricapi-fallback-key.md`. This pass found the admin UI actually **surfaces this key to every admin as an advertised feature**, not an accidental leak an operator would be unaware of:

```tsx
// admin-panel/src/pages/games/Cricket.tsx:444-451
<Alert type="info" message="CricAPI Key Configured"
  description={<span>Paste your API key below to auto-import matches, squads, and flags.
  By default, the system includes a free key: <code>dd511ce4-aeb7-4e1f-86f4-1160404b2776</code>.</span>}
  .../>
```

This doesn't change the underlying risk (the key is still committed to git, still shared across every deployment that never sets its own, still fails silently if the admin-configured key is unset/cleared) but it does mean any operator reading the admin panel already knows a shared fallback exists — the operational blast radius (shared quota, no per-deployment isolation, no signal on exhaustion/revocation) is unchanged and still worth the fix described in the existing bug file.

`sync-api`'s team/status/live-score derivation from the cricapi.com response is heuristic and best-effort: `findFlag()` (`betting.ts:397`) does a bidirectional substring match between team name and cached country name to guess a flag URL (fragile for multi-word country/team names), and `status` is derived as `matchEnded ? 'settled' : matchStarted ? 'live' : 'upcoming'` (`betting.ts:402`) — meaning a sync-triggered `'settled'` transition on `cricket_matches.status` happens **without** ever calling `settleCricketMarket`/`settleCricketSession`/`settleFantasyLeague`. A match can end up `status = 'settled'` in the row while every one of its markets/sessions/fantasy leagues remains `open` with `pending` bets — the admin still has to separately click every "Settle"/"Settle Points" control. This is consistent with the "everything is manual" model described in `docs/games/cricket/overview.md`, just worth noting explicitly: syncing match status from the external API does not settle anything financial.

## `admin-service` routes calling backend endpoints that don't exist

`admin-service` proxies `/api/admin/betting/cricket/sync-series` and `/api/admin/betting/cricket/import-series-matches` to `/internal/cricket/sync-series` and `/internal/cricket/import-series-matches` (`services/admin-service/src/index.ts:1580-1588`) — **neither route exists anywhere in `betting.ts`** (confirmed by grepping the entire `core-api-service/src` tree for `sync-series`/`series_id`/`import-series`: zero matches outside the SQL `series` column name). `docs/backend-services/core-api-service/backend.md` previously noted this gap but concluded it was "currently unreachable from the UI" because it only checked the dead `BettingManagement.tsx`. It is in fact reachable: the live, routed `admin-panel/src/pages/games/Cricket.tsx` has a whole "Import Series" modal (search box + results table + per-row "Import Matches" button, `Cricket.tsx:916-958`) wired to exactly these two proxy routes. This is a genuinely separate gap from the `BETTING_URL` port issue above — even once that's fixed and admin-service can reach `core-api-service` correctly, these two specific routes would still 404, unlike every other cricket admin action which would then start working. See `docs/Bugs/cricket-admin-series-import-routes-missing.md`.
