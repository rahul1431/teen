# Cricket betting — admin panel

The live, routed cricket admin surface is a single page: `admin-panel/src/pages/games/Cricket.tsx` (983 lines), mounted at `/admin/games/cricket` (`admin-panel/src/main.tsx:24,60`, sidebar entry `admin-panel/src/pages/Layout.tsx:30`). It has three tabs: **Matches & Markets**, **Fantasy Contests**, **Live Operators Console**. A second, unrouted copy of the cricket admin UI (`CricketTab` inside `admin-panel/src/pages/BettingManagement.tsx`) is dead code — see `docs/Bugs/orphaned-admin-pages.md`; everything below refers to the live page only.

All write actions proxy through `admin-service` (`services/admin-service/src/index.ts:1507-1593`) to `core-api-service`'s `/internal/cricket/*` routes via the shared `callBetting()` helper, gated by `requireRole('finance')` for money-moving actions (match/market create, settlement, fantasy player/league create, fantasy settlement) and `requireRole('support')` for read-only-ish operational actions (score updates, all three CricAPI sync actions) — `GET`-only routes require just `authenticate`. `callBetting()`'s target URL was misconfigured to a dead port in both the checked-in `.env` and the in-code fallback until fixed 2026-07-28 — see `docs/games/cricket/backend.md` for detail.

## Tab 1 — Matches & Markets

**Cricket Rules & Config card** (`Cricket.tsx:405-442`) — a Form bound to the `cricket` row of `game_configs`: `is_active`, `rake_percent` (0–20%). Submits directly to `PATCH /game-configs/cricket` as flat top-level fields. This card does not render a "Bot Settings" section — cricket's dedicated admin page never had one, and the equivalent dead Bot Settings controls were removed from Aviator/Matka/Lottery's admin pages (fixed 2026-07-28; none of those games have a matchmaking/room concept for bots to fill either). The orphaned `GameConfig.tsx` duplicate (`docs/Bugs/orphaned-admin-pages.md`) still renders an unconditional Bot Settings block for every game type including cricket, but that page is unreachable through the UI.

**CricAPI Integration card** (`Cricket.tsx:444-473`) — lets an admin paste an `api_provider`/`api_key` pair (saved into `game_configs.special_rules`) and exposes three sync buttons:
- **"Sync Countries & Flags"** → `POST /betting/cricket/sync-countries` → `/internal/cricket/sync-countries` — populates `cricket_countries` (id/name/flag URL) used later to auto-guess team flags.
- **"Sync Live/Upcoming Matches"** → `POST /betting/cricket/sync-api` → `/internal/cricket/sync-api` — pulls `currentMatches` from cricapi.com and upserts into `cricket_matches` keyed by `match_api_id`.
- Both buttons work whether or not an API key has been saved, because of the hardcoded fallback (`docs/Bugs/hardcoded-cricapi-fallback-key.md`) — the alert box directly above these buttons tells the admin this in plain text (`Cricket.tsx:444-451`), so this is a documented-in-product default, not a hidden one.

**Import Series** (`Cricket.tsx:478-482, 916-958`) — a "+ Import Series" button opens a modal with a search box and a results table (series name/dates/match count) with a per-row "Import Matches" button. Both the search (`POST /betting/cricket/sync-series`) and the import (`POST /betting/cricket/import-series-matches`) call `admin-service` routes that proxy to `/internal/cricket/sync-series` / `/internal/cricket/import-series-matches` — **neither exists in `core-api-service`**, independent of and in addition to the `BETTING_URL` port misconfiguration noted above: even in a deployment where that's fixed and every other button on this page starts working, "Search"/"Import Matches" would still fail, because there's no route to reach. This entire modal — one of the more polished-looking pieces of the page, with its own loading states and per-row import buttons — has never worked in any deployment. See `docs/Bugs/cricket-admin-series-import-routes-missing.md`.

**Match list** (`Cricket.tsx:477-568`) — every match card shows series/format/teams/flags/status, its markets (each option as a settle button plus a "Void/Refund" button, disabled once `status==='settled'`), and its sessions (numeric "Final Runs" input + "Settle" button). **"+ Add Match"** opens a plain create form (series/format/teams/start time) — this is the fully-manual alternative to CricAPI sync. **"Sync Squad"** (only shown when a match has a `match_api_id`, i.e. it came from a CricAPI sync rather than manual entry) calls `/internal/cricket/sync-squad`, which seeds/updates `cricket_fantasy_players` and `cricket_match_players` rows for both teams from cricapi.com's squad endpoint.

**Settling a market** (`settle()`, `Cricket.tsx:228-239`) — a `Popconfirm` per winning option plus a separate "Void / Refund" `Popconfirm`; both call `POST /betting/cricket/settle` → `settleCricketMarket()` (see `docs/games/cricket/backend.md`). There is no "are you sure, this cannot be undone" language on the win-option confirm (only the Void one says "refund all stakes" in its title) even though settling a market is just as irreversible as voiding it — once `status` flips to `settled`, bets are already marked `won`/`lost` and credited.

**Settling a session** (`settleSession()`, `Cricket.tsx:255-263`) — a bare `InputNumber` (no min/max validation tying it to the session's own `min_runs`/`max_runs` bracket) plus a "Settle" button; there is no confirmation dialog at all for session settlement, unlike every market-settlement action, which does use `Popconfirm`. An admin fat-fingering the wrong number in the "Final Runs" box and hitting Settle immediately triggers real payouts with zero confirmation step.

## Tab 2 — Fantasy Contests

**Matches & Fantasy Pools** (`Cricket.tsx:576-609`) — lists matches with a "Settle Points" button (disabled once `settled`); does **not** show existing leagues per match (the code comment at `Cricket.tsx:604` admits this: "Fetching leagues would require fetching details, for simplicity we show match status and action only"), so an admin creating a second contest for the same match has no visibility into what's already been created without leaving this page.

**Seeded Fantasy Players** (`Cricket.tsx:612-632`) — read-only table of all global `cricket_fantasy_players`, plus "+ Add Player" to manually seed one (name/role/credits 5.0–15.0/team/avatar URL) via `POST /betting/cricket/fantasy/players`.

**"+ Create Contest"** (`Cricket.tsx:862-884`) — creates a `cricket_fantasy_leagues` row: target match, name, entry fee, total prize pool, max entries, and a free-text prize-distribution table parsed from `rank_start|rank_end|payout` lines. No validation in the UI (or the backend Zod schema, `betting.ts:346`) that the sum of tier payouts is affordable within `prize_pool`, or that rank ranges don't overlap/gap — an admin can create a league whose prize tiers sum to more than the stated prize pool, or leave gaps where certain ranks get nothing without it being obviously a "no prize" tier versus a config mistake.

**"Settle Points"** (`handleSettleFantasy()`, `Cricket.tsx:300-318`, modal at `Cricket.tsx:887-914`) — the modal title says "Post Player Performance Scorecard" and the confirm button says "Calculate & Disburse Payouts". Despite the "post a scorecard" framing suggesting an interim/ongoing action, this single click calls `POST /betting/cricket/fantasy/settle` → `settleFantasyLeague()`, which **immediately and irreversibly settles every open league on the match and marks the match itself `settled`** (see `docs/games/cricket/backend.md`). There is no separate "update points, keep contests open" action anywhere in the admin UI or backend — this button can only be used exactly once per match, at the very end. The players shown for scoring are filtered to `p.team_name === settleFantasyFor.team_a || team_b` (`Cricket.tsx:394-396`) client-side, from the same global roster the "Seeded Fantasy Players" table shows — so if squad-sync or manual seeding hasn't happened for a match's two teams, this modal shows "No seeded players found... add players in the global roster tab first," blocking settlement entirely until an admin backfills fantasy players by hand.

## Tab 3 — Live Operators Console

**Active Match Operator Scoreboard** (`Cricket.tsx:641-748`) — a match picker plus a large manual form: match status (upcoming/live/closed/settled), a live-stream URL, runs/wickets/overs, target/runs-required/balls-remaining, two batsmen (name/runs/balls each) and one bowler (name/overs/runs/wickets). "Publish Live Update" sends the whole thing as one JSONB blob to `POST /betting/cricket/scores/update`, which writes to `cricket_matches.live_score` verbatim with no schema validation beyond the Zod `z.any()` on the field (`betting.ts:352`) — whatever shape this form happens to serialize into is exactly what the mobile live-match screen has to defensively parse (see `docs/games/cricket/mobile.md`).

Note this form's own **Match Status** selector can set `status: 'settled'` directly (`Cricket.tsx:659-666`), completely independent of `settleCricketMarket`/`settleCricketSession`/`settleFantasyLeague` — an admin could mark a match `settled` from this console while its markets/sessions/fantasy leagues remain fully open with pending bets, since nothing here calls any settlement function. (Same gap noted for CricAPI's own status derivation in `docs/games/cricket/backend.md`.)

**Live Ball-by-Ball micro-Betting Board** (`Cricket.tsx:750-789`) — "+ Spawn Live Market" reuses the same "Add Market" modal as Tab 1, pre-scoped to the live match, with three extra `market_type` options specific to live betting (`live_ball`, `live_over`, `live_session` — `Cricket.tsx:829-831`) that exist only as string tags with no different handling anywhere in the backend (`cricket_markets.market_type` is an unconstrained `VARCHAR(32)`); they're purely a labeling convention for the admin's own benefit, not a distinct code path.
