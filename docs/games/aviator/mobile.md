# Aviator — Mobile

## Screen and socket client

`mobile/lib/features/games/aviator/aviator_page.dart` is the sole screen (`AviatorPage`, a `StatefulWidget`). It does not use the app's shared `SocketService`/game-gateway connection at all — it owns a dedicated, single-purpose client, `AviatorSocketService` (`mobile/lib/core/socket/socket_service.dart:316-397`), which connects straight to the Aviator engine's own WebSocket at `'$_base/ws/aviator?token=...'` (`:349`). This is architecturally distinct from every other game screen in the app, which talks to `game-gateway`'s single shared `/ws` socket — see `overview.md`/`backend.md` for why (Aviator has no room/gateway integration whatsoever). `AviatorSocketService` reuses the main `SocketService`'s token-refresh logic (`SocketService()._freshToken()`, `:343`) so a stale JWT is refreshed the same way for both sockets, and on a `close(4001)` (bad/expired token) it calls `SocketService().markForceRefresh()` (`:383-386`) to force the *other* socket to refresh too on its next reconnect — a small but real cross-socket coupling between the two independent connections.

Reconnection is exponential-ish backoff capped at 20 attempts: `[2, 2, 4, 4, 8, 8, 16]` seconds cycling by `_reconnectAttempts.clamp(0, 6)` (`:396-397`), then gives up silently (only a debug `print`, no user-facing "can't connect" state beyond whatever `_phase` was left at) — this give-up-with-no-error-state behavior is real regardless of connection outcome, but note the public `/ws/aviator` Nginx path itself was verified working correctly (not misrouted, despite an earlier documentation pass concluding otherwise — fixed 2026-07-28, see `docs/games/aviator/overview.md`).

## Phases and rendering

Local `_phase` state machine: `connecting → betting → flying → crashed → (betting again)`, plus a `maintenance` phase driven by `aviator:maintenance` (server kill-switch, see `admin.md`'s "Game Active" toggle). All phase transitions are driven by server events, never inferred/guessed client-side:
- `aviator:round_start` → `betting`, resets both bet panels, starts a local countdown timer seeded from the server's `betting_time_ms` (`_onRoundStart`, `:140-173`).
- `aviator:flying_start` → `flying`, resets the displayed multiplier to 0 (climbs back to 1.00x+ over the first few animated frames — purely cosmetic; the server's authoritative multiplier and all payout math still start at exactly `1.00x`, per `_onFlyingStart`'s own comment, `:192-204`).
- `aviator:multiplier_tick` → updates `_serverMultiplier` from the server's raw value every ~100ms; the render loop (`_onFrame`, `:336-342`, driven by an `AnimationController` ticking every frame, not `setState`) eases the *displayed* `_multiplier` toward `_serverMultiplier` at a fixed 25%-per-frame rate so the plane glides smoothly between the server's discrete 100ms ticks instead of visibly stepping.
- `aviator:crashed` → `crashed`, snaps the display to the exact revealed `crash_at`, refreshes the wallet balance (`_loadBalance()`), and prepends the crash value to the local history strip.
- `aviator:round_state` → sent once, on connect, so a client that connects (or reconnects) mid-round is brought up to the server's current phase/multiplier/history immediately rather than waiting for the next `round_start`.

`_onTick` also reads an optional `sequence_id` from the tick payload and drops any tick whose `sequence_id` is `<=` the last one seen (`:206-211`, an out-of-order-tick guard). The Aviator engine's actual `aviator:multiplier_tick` broadcast (`services/game-engines/aviator/src/index.ts:356-359`) only ever sends `{ round_id, multiplier }` — it never includes a `sequence_id` field. In practice `seq` is always `null` on the client, so this guard's `if (seq != null && ...)` branch never executes and every tick is always accepted; harmless today (a single WebSocket over TCP delivers frames in order regardless), but it's dead defensive code guarding against a signal the server was apparently meant to send and doesn't.

## Betting and cash-out UI

Two independent bet panels (1 and 2), each with its own stake selector (quick-pick chips ₹10/₹50/₹100/₹500, locked once a bet is placed or the round enters `flying`), its own "Auto Bet" toggle (re-stakes the identical amount automatically at the next `aviator:round_start`, `_onRoundStart:166-172`), and its own "Auto Out" toggle with a stepper target (`1.5x`–`50.0x` client-side range, `_stepBtn` calls clamped in `_buildAutoControls:1078-1107`).

**Placing a bet** (`_placeBet`, `:344-371`): client-side guard checks local `_balance` against the stake and shows "Low balance" if insufficient — this is purely a UX shortcut to avoid a round-trip for an obviously-doomed bet; the actual balance check and fund lock happen server-side (`/internal/wallet/lock` in the engine, see `backend.md`), so a stale/incorrect local `_balance` (e.g. after a bonus credit the client hasn't refreshed yet) cannot let a bet through that the server would reject, nor can it block a bet the server would actually accept. The bet is marked `_betPlaced{1,2} = true` optimistically before the server confirms (`"Optimistic lock"` per the inline comment) — the server's `aviator:bet_placed` push or an `error` event is the actual source of truth; if the server rejects (round moved on, min/max bet violated, insufficient balance) the UI relies entirely on the generic `_onError` handler (`:321-328`) to surface a message, but **does not appear to roll back the optimistic `_betPlaced` flag** — a rejected bet leaves the panel showing "Placed" (button disabled, no error other than a 3-second toast) until the next `aviator:round_start` resets it, meaning a player whose bet was rejected mid-round has no way to place a corrected bet for the remainder of that round even though the server never took their stake.

**Cashing out** (`_cashout`, `:373-381`): only sends `aviator:cashout` if locally believed to be in `flying` phase with an unclahsed placed bet on that panel — purely a client-side guard to avoid a pointless request; the server independently re-validates phase/ownership/already-cashed-out before paying anything (`backend.md`).

**Server-driven auto-cashout** is the primary mechanism (target sent along with the bet in `_placeBet`, executed by the engine on its own authoritative tick — see `backend.md`); the client also runs a **fallback** auto-cashout check in `_onTick` (`:217-230`) for the case where a player flips "Auto Out" on *after* the bet was already placed without a server-known target (`_serverAuto{1,2}` tracks whether the engine actually has a target for that bet). This fallback simply fires the same `aviator:cashout` event once the raw server multiplier crosses the target — it is not a client-computed payout or an early-exit shortcut, so it carries no more trust than a manually-tapped cash-out button; the server still validates and prices it identically.

## Client-side guards vs. server enforcement — what's actually knowable in advance

**The crash point is never knowable or predictable client-side before it happens.** The mobile client receives only: `seed_hash` at round start (a one-way commitment, not reversible to the seed or the crash point), raw `multiplier` ticks as the round progresses (which reveal *that* the plane hasn't crashed yet, not *when* it will), and the actual `server_seed` + `crash_at` only in the `aviator:crashed` event, after the round is already over. There is no code path — official or otherwise — by which the app could compute or guess `crash_at` ahead of the crash; the entire generation happens server-side in `generateCrashPoint` using a seed the client never sees until after the fact (see `backend.md`). Every number the player interacts with in real time (current multiplier, whether they've cashed out, their payout) is either sent by the server or, for auto-cashout targets and bet amounts, sent to the server for it to act on — nothing about the outcome is computed or trusted client-side.

**What is purely cosmetic** (affects only what's rendered, never gameplay/money):
- The 60fps eased "gliding" multiplier display (`_onFrame`) — the real multiplier used for every server decision is `_serverMultiplier`/the raw tick value, never the interpolated `_displayMultiplier`.
- The plane-flight `CustomPainter` (`_AviatorPainter`), star field, propeller spin, thruster glow — pure decoration, `progress` is derived from the interpolated display multiplier only (`(1 - 1/max(_multiplier,1.0)).clamp(0,1)`).
- The "takeoff from 0x" animation at the start of `flying` — actual round math and payouts are keyed to the server's real `1.00x` start, never the animated `0.00` the screen briefly shows.
- The win-burst overlay, haptics, and history-strip coloring — informational, no effect on settlement.

**What is a genuine, if minor, UI defect**: the betting-phase countdown progress bar hardcodes an assumed 5-second window —
```dart
value: (_bettingSecondsLeft / 5).clamp(0.0, 1.0),
```
(`aviator_page.dart`, inside `_buildCenterReadout`'s `betting` branch) — while `_bettingSecondsLeft` itself is correctly derived from the server's actual `betting_time_ms` (`_onRoundStart`, `ms / 1000).ceil()`). The admin panel's "Betting Window (ms)" control (`admin.md`) allows 2000–15000ms, i.e. 2–15 seconds, and the engine broadcasts whatever value is configured. If an admin sets anything other than 5 seconds, the countdown **number** is still correct, but the progress bar is wrong: for a window longer than 5s, `_bettingSecondsLeft/5` exceeds 1.0 and the bar renders fully filled (clamped) for the first `window-5` seconds before finally starting to visibly drain; for a window shorter than 5s, the bar starts already partially empty and empties faster than the countdown text implies. See `docs/Bugs/aviator-mobile-betting-progress-bar-hardcoded-5s.md`.
