# Ludo — Mobile (Flutter)

Seven files under `mobile/lib/features/games/ludo/`: `ludo_modes_page.dart` (entry hub), `ludo_lobby_page.dart` (Quick Match), `ludo_friends_page.dart` (private tables), `ludo_game_page.dart` (the board screen — online and offline share one widget), `ludo_board.dart` (the board/token rendering), `ludo_history_page.dart` (settled-game list), and `ludo_engine.dart` (an offline copy of the server rules for Practice mode).

## Screen flow

`ludo_modes_page.dart` → four mode cards: **Quick Match** (`/games/ludo/lobby`), **Friends** (a bottom sheet → `/games/ludo/friends?mode=create|join`), **Practice** (`/games/ludo/practice`, offline), **History** (`/games/ludo/history`). Mirrors the Teen Patti modes layout by design (per its own header comment).

`ludo_lobby_page.dart` — stake selection (`₹50/100/500` fixed list, not fetched from the server's `stake_options` config — a hardcoded `_stakes` list in the widget, so if `game_configs.stake_options` is ever changed server-side the client's stake buttons won't reflect it without a client release) plus a "Choose Your Colour" seat/color picker — see the seat-preference bug below. Emits `join_matchmaking` over the socket with `{ game_type: 'ludo', stake, preferred_seat? }`, navigates to the board on `room:joined`.

`ludo_friends_page.dart` — private-table create/join/start, reusing the same generic `private:*` socket events Teen Patti's friends flow uses (the gateway routes these by room/table code, not game type). Explicitly caps at Ludo's `max_players` (4, from `game_configs`) with "No bots" advertised in the code-card subtitle — consistent with the gateway's `private:create` handler, which does not auto-fill private tables with bots for any game.

`ludo_game_page.dart` — the actual table, serving both online (`roomId` + `initialData` from `room:joined`) and offline (`offline: true`, local `LudoEngine` vs. 3 bots) through one `StatefulWidget`. Socket listeners: `room:joined` (re-sync/reconnect), `game:state_update` (every roll/move from any seat, human or bot; carries a monotonic `version_id` the client uses to drop stale/out-of-order updates — `if (vid <= _lastVersionId) return`), `game:result` (dedicated end-of-game event — the client deliberately ignores any embedded `result` field on `game:state_update` broadcasts and only reacts to this dedicated event, with an inline comment explaining that acting on both previously double-fired the win/lose dialog, confetti, and sound), `error` (surfaced as both a banner and a snackbar — including AFK auto-play notifications, "You took too long..."), `room:chat`/`room:tip` (emoji reactions and dealer tips — shared, game-agnostic gateway events).

`ludo_history_page.dart` — paginated `/api/wallet/game-history?game_type=ludo`, same generic wallet endpoint Teen Patti's history page uses.

## Board rendering (`ludo_board.dart`)

Coordinate tables (`_track`, `_homeLanes`, `_baseDots`) are hand-authored 15×15 grid positions matching a standard Ludo King–style board; `_BoardPainter` draws the four coloured quadrants, path cells, safe-cell stars, home-lane arrows, and the four-triangle center regardless of how many seats are actually occupied (a 2-player game simply renders two quadrants with populated token trays and two with empty ones — there's no player-count-aware layout variant). The whole board rotates via `_tokenPixel`/`_BoardPainter`'s `rotationAngle` so the local player's own seat always renders at the bottom regardless of their actual `seat` number — a standard "always render yourself at the bottom" UX convention, computed purely client-side from `mySeatIndex`.

Token movement is animated cell-by-cell (`_TokenSprite._animateSteps`), with a distinct capture animation (`_animateCapture`, slides back to base) and a home-arrival bounce (`_fx` flourish), plus per-cell "tik" stepping sounds and a safe-cell chime. Overlapping tokens on one cell are visually clustered with small diamond/offset patterns that scale down as more tokens share a cell (2 → 0.75 scale, 3 → 0.68, 4 → 0.60).

### The "cluster finished tokens" commit is a mobile-only visual fix, not an engine change

The most recent Ludo-tagged commit at the time of writing, `0d2e03a fix(ludo): cluster finished tokens tightly instead of spreading toward triangle edge`, touches exactly two files: `mobile/lib/features/games/ludo/ludo_board.dart` and `mobile/pubspec.yaml` (a version bump) — **no engine or gateway files**. The change replaced a previous linear "spread along one axis" placement for multiple same-color finished tokens with `_goalCentroid()` (`ludo_board.dart:185-197`), which anchors all finished tokens of a seat at their goal triangle's true centroid and folds them into the same diamond overlap-offset grouping already used for tokens sharing any other cell — matching the visual style used everywhere else on the board. This is purely a rendering fix (where finished tokens sit inside their goal triangle); it has no bearing on server-side rules, win detection, or the money path, and is worth calling out precisely because the commit message alone ("fix(ludo)") could be misread as an engine change during the git-log skim in `overview.md`.

## Offline Practice mode (`ludo_engine.dart`)

A from-scratch Dart port of `services/game-engines/ludo/src/rules.ts` — same constants (`kMainTrack=52`, `kHomeProgress=57`, `kStartOffsets`, `kSafeCells`), same `movableTokens`/`applyRoll`/`applyMove`/`captureAt`/`passTurn`/`chooseBotToken` logic, ported by hand rather than shared via any code-generation or shared-package mechanism. The file's own header comment flags this explicitly: "The rules here are a faithful port of `rules.ts` — keep them in sync." This is a real maintenance hazard (two independent implementations of real-money-adjacent game rules that must be manually kept identical), but the actual blast radius is contained: Practice mode is stake-free (`stake: 0`, hardcoded `roomId: 'PRACTICE'`) and never touches the wallet or a real room, so a rules divergence here would only affect the offline single-player experience, not settlement correctness.

`chooseBotToken` in the Dart port is notably **simpler** than the server's three-difficulty version — it always plays "prefer a capture, else advance the furthest token" (roughly the server's `medium` behavior) with no `easy`/`hard` branching and no difficulty parameter at all. Practice-mode bots are therefore always one fixed difficulty regardless of anything else, which is a cosmetic/product-parity gap (a player who wants to practice against "hard" bots specifically cannot, offline) rather than a bug.

## Server-authoritative vs. cosmetic-only: the AFK timer comparison

The gateway's per-turn AFK auto-play timer is genuinely server-authoritative for Ludo (`docs/backend-services/game-gateway/backend.md`: `LUDO_TURN_TIMEOUT_MS = 30000`, `scheduleLudoAfkTimer`/`autoPlayIdleLudoTurn` — re-armed on every state transition via `driveLudoBots()` being called after every human action). Teen Patti has an equivalent (`scheduleTeenPattiAfkTimer`/`autoFoldIdleTeenPattiTurn`, same 30s duration, live since 2026-07-12 — an earlier pass of this doc incorrectly claimed Teen Patti had none). Both games' client-side "your turn" countdowns are therefore visualizing a real, server-enforced deadline, not decoration. Ludo's does so imperfectly:

`ludo_game_page.dart:56-87` (`_syncTurnTimer`) runs a **client-only** cosmetic countdown ring (`CircularProgressIndicator` around the acting player's avatar, `_buildCornerPlayer`) from a hardcoded `_turnTimerSeconds = 30`, active only while `_isMyTurn && _state?.awaiting == 'roll' && !_rolling && !_botBusy`. The duration itself matches the server's `LUDO_TURN_TIMEOUT_MS = 30000` (raised from 25s to 30s specifically to match the client, back on 2026-07-09) — but there's a real phase gap: the countdown's `active` condition requires `awaiting == 'roll'`. The server's AFK timer, however, is armed the moment it becomes a human's turn and stays armed through the `'move'` phase too (re-armed via `driveLudoBots()` being invoked again after the human's roll transitions `awaiting` to `'move'`) — `autoPlayIdleLudoTurn()` explicitly branches on `awaiting === 'move'` to auto-play the first legal token if that's what timed out. So a player who rolls and then hesitates over which token to move gets **no visible countdown at all** during that window (`active` goes false the instant `awaiting` flips away from `'roll'`), yet the server will still auto-play a move for them 30 seconds after their turn started if they don't act — an invisible deadline during exactly the phase where a real decision (which token to move) is being made. (There's also a third, unrelated number in play: the DB migration's `special_rules.turn_timeout_seconds = 20`, which nothing reads at all — see `backend.md`'s AFK-timer section and `docs/Bugs/ludo-turn-timeout-config-not-wired.md`.)

See `docs/Bugs/ludo-client-afk-countdown-mismatched-duration.md` (scope narrowed 2026-07-29 — the duration-mismatch half of that report was itself stale).

## "Choose Your Colour" — the guarantee is honored server-side

`ludo_lobby_page.dart:340-364` — a "CHOOSE YOUR COLOUR" seat picker lets the player tap one of the four seat colors before Quick Match, labeled `'(optional)'` when unset and **`'guaranteed'`** once a color is picked (`:344-353`). The chosen value is sent as `preferred_seat` in the `join_matchmaking` payload (`:94-98`, `:53-57` on reconnect).

The gateway does read and honor this field (an earlier pass of this doc incorrectly claimed otherwise). `index.ts`'s `'join_matchmaking'` handler validates `data.preferred_seat` as an integer 1-4 and passes it through `joinQueue()` as `MatchmakingEntry.preferredSeat`. `startGame()`'s `orderBySeatPreference()` (`matchmaking.ts`) then places each real player with a preference at the array index matching their chosen seat (first-come-first-served by queue order; a conflicting/already-taken preference falls through to the next free seat, along with any player who expressed no preference), before filling remaining slots with bots. Games with no preference expressed at all keep the legacy `[...real, ...bots]` order untouched. This has been wired up since 2026-07-09.

## Other cosmetic-vs-server-enforced notes

- The win/loss result dialog, standings list, and prize amount are all driven off the server's dedicated `game:result` payload (`winner_id`, `rankings`, `prize`) — none of it is client-computed for online play (the `_winningAmount` getter shown in the app bar during play is a client-side estimate for display only, using the same 5%-rake formula as the server for consistency, but the actual payout dialog uses the server's own `prize` value).
- Capture/home sound effects for online games are inferred client-side by diffing token state between successive `game:state_update` payloads (`_detectCapture`/`_detectHome`, counting base-token/finished-token deltas) rather than being told explicitly by the server — a reasonable approach since the wire format doesn't carry a discrete event type for these, but it means any future server-side state shape change that doesn't preserve these exact counting semantics would silently break just the capture/home sound cues without affecting gameplay correctness.
- The emoji tray's contents come from `/api/admin/config/emojis` (shared with Teen Patti) with a hardcoded fallback list on any fetch failure — never blocks the game from loading.
