# Wallet Service — Backend

All routes live in `services/wallet-service/src/index.ts`; ledger mutation logic lives in `services/wallet-service/src/wallet.service.ts` (`WalletService`). Two auth guards: `authenticate` (player JWT via `@fastify/jwt`, `req.jwtVerify()`) and `authenticateInternal` (`x-internal-key` header must equal `INTERNAL_SERVICE_KEY`, fails closed if either side is unset — `src/index.ts:98-102`). No global Zod error handler is registered, so any `.parse()` failure throws and Fastify returns a bare 500 with no useful body — this class of issue previously bit a real caller (`POST /api/admin/users/:id/debit` was missing `request_id`), fixed 2026-07-28.

## Ledger core (`wallet.service.ts`)

`credit()`/`debit()` both: `SELECT ... FROM wallets WHERE user_id = $1 FOR UPDATE` (row lock), compute `balanceAfter`, `INSERT INTO wallet_transactions (...) VALUES (...) ON CONFLICT (idempotency_key) DO NOTHING RETURNING id` (idempotency — `wallet_transactions.idempotency_key` is `UNIQUE NOT NULL`, enforced at the DB level since `infra/db/migrations/024_wallet_idempotency_unique.sql`, which replaced an earlier select-then-insert race), and only if the insert actually returned a row do they `UPDATE wallets SET <col> = balanceAfter`. `debit()` additionally throws `Insufficient balance` if `balanceBefore < amount` before ever touching the row. Both accept an optional caller-provided `PoolClient` so they can be composed into a larger transaction (used by `/wallet/deposit/verify`). `wallets.real_balance`/`bonus_balance`/`locked_balance` all carry `CHECK (>= 0)` constraints (`infra/db/migrations/001_initial.sql:72-74`) — a second line of defense against any code path that computes a negative balance.

`lockForGame(userId, amount, roomId, lockId)` — moves `real_balance → locked_balance`, idempotency key `lock:<lockId>` (caller-generated per lock attempt, not per room, so multiple distinct bets in the same room each get their own key). `unlockFunds` — reverses a lock, key `unlock:<roomId>:<userId>` (deterministic, safe to call from multiple places — game-start rollback and the idle-room watchdog both call it for the same room/user without double-refunding). `consumeLockedFunds` — `locked_balance -= amount` when a bet/entry-fee is actually spent, key `consume:<roomId>:<userId>` when a room ID is given. Both `unlockFunds` and `consumeLockedFunds` *clamp* to `min(locked, amount)` rather than throwing when `locked < amount`, logging a warning — a deliberate design choice to keep settlement from crashing on minor discrepancies, but it also means a caller passing a wrong `amount` silently gets a partial unlock/consume instead of an error.

## Player-facing routes (JWT auth)

- **`GET /wallet/balance`** — returns `{ real_balance, bonus_balance, locked_balance }` from `wallets`.
- **`GET /wallet/game-history?game_type&limit&offset`** — joins `game_participants`/`game_rooms`, computes `net_result` per completed game the caller played (excludes bots).
- **`GET /wallet/transactions?limit&offset`** — paginated `wallet_transactions` for the caller (`WalletService.getTransactions`).
- **`POST /wallet/deposit/create-order`** — `{ amount: 10-100000 }` (hardcoded range, see `docs/Bugs/wallet-service-deposit-withdrawal-limit-env-vars-are-dead-config.md`). 503s if Razorpay isn't configured. Creates a Razorpay order and an `payment_orders` row (`status='created'`, `gateway='razorpay'`). **Dead client-side**: no mobile code calls this route or `/wallet/deposit/verify` (grepped `mobile/lib` for `razorpay`/`create-order`/`deposit/verify` — zero hits outside the unused `AppConfig.razorpayKeyId` constant); manual UPI/bank deposit (`/wallet/deposit/submit` below) is the only live deposit path.
- **`POST /wallet/deposit/verify`** — verifies `razorpay_signature` via `HMAC-SHA256(order_id|payment_id, RAZORPAY_KEY_SECRET)` (plain `!==` comparison, not constant-time — low practical risk given this also requires a valid `order_id` that must already exist in `payment_orders` with `status='created'`). On match: marks the order `paid` and calls `walletSvc.credit(..., client)` **inside the same DB transaction** as the order update (`src/index.ts:193-215`), then fires `tryTriggerReferralReward` (see below) outside that transaction.
- **`GET /wallet/deposit/methods`** — active rows from `payment_methods` (admin-managed, see admin.md), ordered by `sort_order`.
- **`POST /wallet/promo/validate`** — `{ code, amount }`. Checks `promo_codes` active/not-expired/under `usage_limit`, then per-user usage against `promo_code_usages` (`UNIQUE(promo_id, user_id)`), computes `discount_amount`/`bonus_amount` (percent or fixed, capped by `max_discount`). Read-only — does not reserve/consume the code.
- **`POST /wallet/deposit/submit`** — multipart: `amount`, `payment_method_id`, `reference_number` (UTR), optional `promo_code`, and a file (jpg/jpeg/png/webp/pdf, streamed to `UPLOAD_DIR` under `<userId>_<uuid>.<ext>`). Re-validates the promo code and computes the bonus again server-side (never trusts the client's number). Inserts a `payment_orders` row (`status='created'`, `gateway='manual'`) with the promo bonus stashed in `metadata`. Does **not** credit anything — an admin must approve it (`PATCH /api/admin/finance/deposits/:id`, see admin.md) before the wallet moves. Promo usage bookkeeping (`INSERT INTO promo_code_usages ... ON CONFLICT DO NOTHING` + `UPDATE promo_codes SET used_count = used_count + 1`) happens here, at submit time, not at approval time — and the `used_count` increment isn't gated on whether the insert actually happened, so two racing submits from the same user with the same code can double-increment `used_count` even though the per-user `UNIQUE` constraint prevents a second usage row.
- **`POST /wallet/withdraw/request`** — `{ amount: 100-50000, bank_account?, upi_id? }`. Requires `users.kyc_status = 'approved'` first. Locks the amount inside a transaction (`SELECT ... FOR UPDATE` on `wallets`, `real_balance -= amount`, `locked_balance += amount`), creates a `payment_orders` row (`type='withdrawal'`, `status='created'`), and logs a `status='pending'` `wallet_transactions` row with key `withdraw:<orderId>`. No idempotency key is accepted from the client for this route — a double-submit creates two independent locks (the mobile client guards against this with a `_submitting` flag, `mobile/lib/features/wallet/wallet_page.dart:939`, but nothing server-side stops it).

## Internal routes (`x-internal-key` auth, called by other services)

- **`POST /wallet/deposit/manual`** — admin-only credit path (also reachable at this non-`/internal`-prefixed path despite the auth guard). `{ user_id, amount, request_id, description? }`; `request_id` becomes idempotency key `manual_credit:<request_id>`. Also triggers `tryTriggerReferralReward`.
- **`POST /wallet/debit/manual`** — same shape, `manual_debit:<request_id>`, returns 400 `Insufficient balance` if the debit would go negative.
- **`POST /internal/wallet/lock`** — `{ user_id, amount, room_id, lock_id? }`; generates a `lock_id` if the caller doesn't supply one. Called by `game-gateway` before a game starts and per-bet during play.
- **`POST /internal/wallet/unlock`** — `{ user_id, amount, room_id }`; called on game-start rollback, room termination, and by `GameWatchdog` (`services/game-gateway/src/watchdog.ts`) when reaping idle rooms.
- **`POST /internal/wallet/consume`** — `{ user_id, amount, room_id }`; called by `admin-service`'s withdrawal-approval transition (using `room_id: "withdrawal:<orderId>"` as the dedupe key, not an actual game room).
- **`POST /internal/wallet/settle-game`** — `{ room_id, winner_id, prize, players: [{user_id, entry_fee}] }`. Consumes each player's locked entry fee independently (non-fatal per-player, collected into `consume_errors`), then credits the winner unconditionally if `prize > 0`, key `win:<roomId>:<winnerId>`. A per-player consume failure here used to strand that player's stake in `locked_balance` forever — fixed 2026-07-28: `game-gateway`'s `GameWatchdog` now sweeps recently-completed rooms every 5 minutes and retries any missing `consume:<roomId>:<userId>` transaction (see `docs/backend-services/game-gateway/backend.md`), and both `matchmaking.ts` callers now log loudly (instead of discarding) when a successful response still carries `consume_errors`.
- **`POST /internal/wallet/credit`** — `{ user_id, amount, type, reference_id?, idempotency_key, description? }`. `type` must be one of `game_credit | bonus | referral | manual_credit`; `bonus`/`referral` are hardcoded to land in the **bonus** wallet ("promotional money is never withdrawable", `src/index.ts:586-589`) — the referral page's copy that used to contradict this ("credited to your real balance") was corrected 2026-07-29, see `docs/app/referral/mobile.md`. `amount` has no `.positive()` constraint in the Zod schema — a negative amount would be accepted and effectively debit the target wallet without going through `debit()`'s insufficient-balance check, though the `wallets` table's `CHECK (>= 0)` constraint still blocks it from going negative (throws a generic DB error instead of a clean 400).
- **`POST /internal/wallet/debit`** — `{ user_id, amount (positive), reference_id?, idempotency_key, description? }`, `type` hardcoded to `game_debit`. Used by the betting flows (Matka/Lottery/Cricket) in `core-api-service` to take a stake.

## Referral reward side-effect

`tryTriggerReferralReward(userId, db, walletSvc)` (`src/index.ts:21-71`) runs after every successful deposit (Razorpay-verified or admin-approved manual). It looks for a `pending` row in `referrals` where `referee_id = userId`, locks it (`SELECT ... FOR UPDATE`), flips it to `rewarded` in its own transaction, then calls `walletSvc.credit(..., walletType: 'bonus')` for the referrer with key `referral_reward:<referralId>` — idempotent, and non-fatal on failure (caught and logged so a referral-crediting bug never blocks the deposit itself).

## Direct-write ledger paths outside `wallet-service`

Several ledger writes happen without ever calling this service, going straight to `wallets`/`wallet_transactions` from `game-gateway`'s own DB pool: the `room:tip` WS handler (`services/game-gateway/src/index.ts`, its previously non-deterministic idempotency key was fixed 2026-07-28 — a `tip:lock:<userId>:<roomId>` Redis NX lock now blocks a double-tap/retry from double-debiting, with a deterministic `idempotency_key` as a DB-level backstop) and `autoRefillBots` (`services/game-gateway/src/matchmaking.ts:201-239`, tops bot wallets back up to ₹10,000 when low). Both implement their own `BEGIN`/`FOR UPDATE`/`COMMIT` transactions rather than reusing `WalletService`, so their correctness guarantees have to be independently verified rather than inherited. `tip_dealer` was added to the Postgres `txn_type_enum` in `infra/db/migrations/029_tip_dealer_drop_gifts.sql` but was never added to `WalletService`'s own `TxnType` TS union (`wallet.service.ts:4`) — harmless today since these writers never go through `WalletService`, but a latent trap if anyone later routes tips through it.
