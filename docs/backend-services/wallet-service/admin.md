# Wallet Service — Admin-panel touchpoints

The admin panel never talks to wallet-service directly (no `WALLET_SERVICE_URL`/`3003`/`/wallet/` reference anywhere under `admin-panel/src`) — it only talks to `admin-service`, which itself either calls wallet-service's internal/manual endpoints for *mutations* or reads the same Postgres tables (`wallets`, `wallet_transactions`, `payment_orders`, `game_rooms`) directly for *reads*, bypassing wallet-service entirely. This split matters: anything read-only in the Finance/Users pages reflects the DB straight, with no wallet-service business logic in between (e.g. no re-validation of idempotency, no re-derivation of `pnl`).

## `admin-panel/src/pages/Finance.tsx`

- **Withdrawals tab** — `GET /api/admin/finance/withdrawals?status=` lists `payment_orders` (`type='withdrawal'`) directly (`services/admin-service/src/index.ts:601-610`, no `requireRole` beyond `authenticate`). Approving/rejecting/reverting calls `PATCH /api/admin/finance/withdrawals/:id` (`requireRole('finance')`, `services/admin-service/src/index.ts:616-764`), which drives a 6-way status state machine (`created ↔ paid ↔ refunded`) and, for each transition, calls one of wallet-service's `/internal/wallet/consume`, `/internal/wallet/unlock`, `/internal/wallet/credit`, or `/wallet/debit/manual` to actually move money — **without checking the response** (`fetch(...).catch(...)`, no `res.ok` check). See `docs/Bugs/withdrawal-state-machine-ignores-wallet-service-failures.md` — a wallet-service-side rejection here is invisible to the admin and does not block the status change, audit log entry, or player push notification.
- **Deposits tab** — `GET /api/admin/finance/deposits` (`requireRole('finance')`) lists `payment_orders` (`type='deposit'`). `PATCH /api/admin/finance/deposits/:id` with `action: 'mark_paid_and_credit'` calls `POST /wallet/deposit/manual` to credit the user, then `tryTriggerReferralReward`'s server-side counterpart runs inside wallet-service itself. Same unchecked-`fetch` pattern as withdrawals, and here the DB status update to `'paid'` happens *before* the wallet call is confirmed — see the same bug doc for the ordering detail.
- **Ledger sub-view** — `GET /api/admin/finance/ledger` (`requireRole('finance')`) is a filtered/paginated read straight against `wallet_transactions` (type, wallet_type, user_id, date range).
- **Reconciliation sub-view** — `GET /api/admin/finance/reconciliation` aggregates `payment_orders` by day/gateway/status and `game_rooms.platform_fee_collected` (the "GGR" figure) — note `platform_fee_collected` is written by the Go Teen Patti engine (`services/game-engines/teen-patti/main.go:803`), not by wallet-service, and has no linkage back to specific `wallet_transactions` rows, so this reconciliation view can't itself detect an orphaned-lock scenario — that's now handled separately by `game-gateway`'s `GameWatchdog` completed-room reconcile sweep (fixed 2026-07-28, see `docs/backend-services/game-gateway/backend.md`), not this view.
- **Stats cards** — `GET /api/admin/finance/stats` sums `platform_fee_collected` (revenue) and `payment_orders.amount` (deposits/withdrawals) for today/month, again reading tables directly.
- **Tips sub-view** — `GET /api/admin/finance/tips` reads `wallet_transactions WHERE type='tip_dealer'` (the ledger rows written directly by `game-gateway`, not through wallet-service — see backend.md).

## `admin-panel/src/pages/Users.tsx`

`ProfileTab`'s **Credit Wallet** / **Debit Wallet** buttons (`requireRole('finance')` on the backend) call `POST /api/admin/users/:id/credit` and `POST /api/admin/users/:id/debit` (`services/admin-service/src/index.ts:331-366`), which proxy to wallet-service's `/wallet/deposit/manual` and `/wallet/debit/manual` respectively — credit works, debit is currently broken (missing `request_id`, see `docs/Bugs/users-page-debit-wallet-missing-request-id.md`). The Users list itself computes a `pnl` column server-side in `admin-service` via a `SUM(CASE WHEN type='game_credit' ...)` over `wallet_transactions` (`services/admin-service/src/index.ts:303-310`) — another direct read. `GET /api/admin/users/:id/transactions` is a plain `wallet_transactions` read, no role gate beyond `authenticate`.

## Payment methods & promo codes (feed wallet-service's own routes)

`admin-panel` manages `payment_methods` (`GET/POST/PATCH /api/admin/payment-methods`, `requireRole('finance')`; `DELETE` requires `requireRole('superadmin')`) and `promo_codes` (`GET/POST/PUT/DELETE /api/admin/promo-codes`) entirely through `admin-service`, writing straight to those tables — `admin-service` never calls wallet-service for this. wallet-service only *reads* these tables at request time (`GET /wallet/deposit/methods`, `POST /wallet/promo/validate`, `POST /wallet/deposit/submit`), so an admin toggling `payment_methods.is_active` or editing a promo's `usage_limit` takes effect on the player app immediately with no wallet-service restart or cache to invalidate.

## RBAC

Roles are hierarchical (`services/admin-service/src/index.ts:37`, `ROLE_INDEX: { readonly: 0, support: 1, finance: 2, superadmin: 3 }`), `hasRole` checks `>=`. All wallet-mutating admin routes require at least `finance`; deleting a payment method requires `superadmin`. There is no wallet-service-side awareness of admin roles at all — every admin-triggered wallet mutation is authenticated purely by `INTERNAL_SERVICE_KEY`/`x-internal-key`, identical to how `game-gateway` authenticates; wallet-service cannot distinguish "admin-service acting on behalf of a finance admin" from "game-gateway settling a hand" beyond the endpoint path itself.
