# Teen Patti Engine — Mobile (Flutter) consumption

The Flutter client never talks to this engine directly — it only ever sees this engine's output relayed through `game-gateway`'s WebSocket (`docs/backend-services/game-gateway/frontend.md` covers the shared transport layer: `SocketService`, reconnect/backoff, JWT handshake). This file covers what the Teen Patti-specific screens do with the payloads that originate from this engine's `GameState`/`GameResult` structs.

Primary file: `mobile/lib/features/games/teen_patti/game_page.dart` (3,874 lines — the largest single screen in the mobile app). Also relevant: `mobile/lib/features/games/teen_patti/lobby_page.dart` (variant/stake selection, pre-deal), `mobile/lib/core/constants/socket_events.dart` (event-name constants).

## Table variant selection happens client-side, before this engine is ever called

`TeenPattiLobbyPage` takes a `variation` constructor parameter (`classic` default, or `ak47`/`muflis`/`joker`/`no_limit`), one per lobby entry point in the game-select UI. It's purely cosmetic/routing at this layer — the actual per-variant rule text, icon, and accent gradient (`_variationLabel`/`_variationRule`/`_variationIcon`/`_variationGradient`) are static client-side lookups keyed by the string, not anything this engine returns. The chosen `variation` is sent as-is in the `join_matchmaking` payload and flows through unchanged to this engine's `StartGameReq.Variation` (`docs/backend-services/game-gateway/backend.md`'s matchmaking section, `matchmaking.ts:255-540`). This engine has no say in which variants exist for a player to choose — see `admin.md` for the corresponding admin-side gap.

## Consuming `room:joined` / `game:state_update` (this engine's `GameState`)

`_applyRoomJoinedData` (`game_page.dart:250-283`) and the `game:state_update` listener (`:323-355`) both normalize the same shape: `data['state']` (or `data` itself) is this engine's `GameState` JSON, snake_case as emitted by Go's `json` tags (`current_turn`, `min_bet`, `is_seen`, `joker_value`, `pot_limit`, etc.) — `_mapPlayers` defensively backfills both `user_id`/`userId` on every player entry (`:227-233`) in case anything upstream re-cases the field, but the engine itself only ever emits `user_id`.

Specific fields consumed:
- **`current_turn`** (index into `players`) — compared against the locally-stored user ID to decide `_myTurnNotifier`, which drives whether the action bar is interactive and whether `_startTurnTimer()` fires.
- **`min_bet`** — used both to compute `_actionCost()` for the "guarded action" balance pre-check (`_guardedAction`, `:699-707`, which shows a "Low Balance" dialog with a Pack option rather than letting a doomed action reach the server and silently fail) and as the default raise amount.
- **`pot`**, **`pot_limit`** — displayed directly; `_potLimitOf` (`:2139-2140`) reads either `pot_limit` or a legacy `potLimit` camelCase key defensively.
- **`variation`** + **`joker_value`** — `_buildVariantChip` (`:2088-2106`) renders a persistent on-table pill: `"🔻 MUFLIS · Lowest hand wins"`, `"🃏 JOKER · All {joker_value}s are wild"` (falling back to a generic label if `joker_value` is empty), `"✨ AK47 · A · K · 4 · 7 are wild"`. This is the client's only per-hand indication of which rank is wild in Joker mode — it reads `joker_value` (the display string, e.g. `"9"`/`"K"`) directly off this engine's `GameState.JokerValue` field, not `joker_rank`.
- **`my_cards`** (from `room:joined` only, a gateway-added field not on `GameState` itself — the gateway filters `Player.Cards` per-recipient before broadcasting, per `docs/backend-services/game-gateway/backend.md`) — this engine's own `GameState.Players[i].Cards` would leak every seat's hand if it ever reached the client unfiltered; the client has no defense against that itself, it depends entirely on the gateway's filtering. This engine's own `/state` endpoint has no per-recipient filtering of its own either, but it's no longer reachable without the internal service key (fixed 2026-07-29, `backend.md`), so an unfiltered client was never actually exposed to it.

## Sideshow flow (`game:sideshow_prompt` / `game:sideshow_reveal` / `game:sideshow_result`)

These three events (no constants in `socket_events.dart` — handled by string literal, per `docs/backend-services/game-gateway/frontend.md`'s note about undocumented event names) correspond directly to this engine's `PendingSideshow` sub-state machine (`backend.md`): a `"sideshow"` action's `response["sideshow_request"]` becomes `game:sideshow_prompt` to the target only, `sideshow_accept`'s `response["sideshow_reveal"]` (which includes both players' actual cards) becomes `game:sideshow_reveal` to the two involved players only, and `sideshow_reject`'s `response["sideshow_rejected"]` becomes a card-free `game:sideshow_result` to the room. `_sideshowPromptTimer` (`:529-582`) runs a client-side countdown on the prompt dialog; if it's the local player being asked and they don't respond, nothing in the client auto-answers — see the turn-timer note below for the parallel gap on the requester's side.

## The client-side turn timer duplicates a server-side one that also exists

`_startTurnTimer()` (`:658-677`) starts a 30-second `Timer.periodic` the moment the state update marks it the local player's turn, sending haptic pulses and auto-issuing a `fold` action if it reaches zero (`_sendAction('fold')`, `:674`). This matches `resources/game-configs/teen-patti.json`'s `table.turnTimeoutSeconds: 30` almost exactly — but it is a **purely client-side, best-effort UX feature**, not what actually enforces the timeout: it only fires if the app is foregrounded, the timer isn't garbage-collected, and the socket is connected enough for the resulting `fold` emit to reach the gateway. A backgrounded, force-quit, or disconnected app never runs this code — but `game-gateway`'s own `scheduleTeenPattiAfkTimer`/`autoFoldIdleTeenPattiTurn` (`docs/backend-services/game-gateway/backend.md`) independently arms the same ~30s window server-side and auto-folds regardless of client state, so a genuinely stuck/offline human is unstuck within ~30s either way, not just by the 15-minute room-level watchdog.

## Sending actions back (`_sendAction`, `:773+`)

Emits `SocketEvents.gameAction` (`'game:action'`) with `{ room_id, action, amount, sequence_num }` — note this engine decodes `sequence_num` but never uses it (`backend.md`), so whatever the client sends here has no server-side effect beyond being logged in the request. `_actionCost()` (`:680-695`) mirrors this engine's own cost rules client-side purely for the pre-flight balance check (`isSeen ? stake*2 : stake` for call/show, `stake*2` for sideshow) — it is calculated independently from, and must be kept manually in sync with, the identical arithmetic inside `main.go`'s `processAction` (`callAmount`/`showCost`/sideshow `cost`). The client itself still imposes no ceiling on the `raise` amount it lets a player submit via the bet slider (`_actionCost`'s `raise` case just echoes back whatever `amount` was chosen, `:686-687`) — but as of 2026-07-29 the engine now rejects an oversized raise server-side (`maxRaiseFor`, `backend.md`'s "Pot limits" section), so an over-the-cap client submission now surfaces as a rejected action rather than silently succeeding and forcing every bot at the table to fold (`docs/Bugs/teen-patti-unbounded-raise-forces-bot-fold.md`, fixed).

## Result screen (`game:result`)

`_gameResultSub` (`:380-429`) reads `data['result']` (this engine's `GameResult`), pulling `hand_rank` (a human-readable string like `"Trail"`/`"Pure Sequence"` from `handRankName()`) either off the winner's entry in `all_hands` or the top-level `hand_rank` field, and displays it alongside the prize amount. `all_hands` (every non-folded player's cards, sent unconditionally by this engine in every `GameResult`) is what powers the post-hand reveal of opponents' cards — by hand-completion time there's no privacy concern left, so no filtering is needed or applied at this stage, unlike mid-hand state updates.
