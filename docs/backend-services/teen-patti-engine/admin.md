# Teen Patti Engine — Admin-panel touchpoints

There is no admin-panel page dedicated to this engine specifically. What control exists is split across three unrelated surfaces, two of which are less connected to the real engine behavior than they appear.

## `games/registry.json` and `resources/game-configs/teen-patti.json` — static, not live

`games/registry.json` lists Teen Patti with `"config": "resources/game-configs/teen-patti.json"`. That JSON file (`bootAmount`, `stakes`, `table.turnTimeoutSeconds: 30`, `bots.fillAfterSeconds`, `bots.maxBotsPerTable`, `betting.maxChaalMultiplier`, `betting.maxPotLimitMultiplier`, etc.) is **never read by any running service** — confirmed by grepping `services/**` and `admin-panel/**` for `game-configs` path references; the only hits are the registry file itself and unrelated admin-panel pages that happen to share the phrase "game config" in their own names. It functions purely as a checked-in reference/seed document, not a runtime config source.

Two concrete consequences worth knowing:
- `table.turnTimeoutSeconds: 30` in this file happens to match reality even though it's never read: `game-gateway/src/matchmaking.ts`'s `TEEN_PATTI_TURN_TIMEOUT_MS` (`scheduleTeenPattiAfkTimer`) is also 30 seconds, same as `LUDO_TURN_TIMEOUT_MS`. The coincidence is exactly that, though — this JSON value isn't the source of either constant, it just happens to agree with the gateway's own hardcoded one for Teen Patti.
- `betting.maxChaalMultiplier: 4` implies a cap on how large a single raise/chaal can be relative to the current stake. This JSON file still isn't read at runtime, but as of 2026-07-29 `main.go`'s `"raise"` branch enforces the equivalent cap itself, via a hardcoded Go constant of the same value (`maxChaalMultiplier`, `main.go`) rather than by reading this file — see `docs/backend-services/teen-patti-engine/backend.md`'s "Pot limits" section. There is still no admin-facing way to change this multiplier without editing and redeploying the Go source (the same governance gap `docs/Bugs/teen-patti-dda-admin-control-gap.md` describes for `win_rate_target`).

## The real live config: Postgres `game_configs`, via `GameConfig.tsx`

`admin-panel/src/pages/GameConfig.tsx` renders one card per row of the Postgres `game_configs` table (`GET /api/admin/game-configs`, `services/admin-service/src/index.ts:1025-1028`) and saves via `PATCH /api/admin/game-configs/:gameType` (`:1031-1046`, `requireRole('superadmin')`). For `teen_patti` this table exposes: `is_active`, `rake_percent`, `bot_fill_enabled`, `bot_fill_delay_seconds`, `max_bot_ratio`, `bot_fill_table_size`, `bot_difficulty`. Two of these reach this engine directly:
- **`rake_percent`** — read fresh from Postgres by this engine on every single showdown (`loadRakePct`, `main.go:730-742`). This is the one config value the engine consults live, with no caching layer in between — an admin's save takes effect on the very next hand that reaches showdown.
- **`bot_difficulty`** — read by `game-gateway`'s `matchmaking.ts` (not this engine) at room-creation time and passed through as `StartGameReq.BotDifficulty` in the `/start` call (`docs/backend-services/game-gateway/backend.md`). This is what selects which `bot_profiles` row (`easy`/`medium`/`hard`) the DDA lookup in `startGame` uses — i.e., the single admin-facing lever that indirectly controls how aggressively the DDA card-swap targets a human (see `backend.md`'s DDA section for what "hard" actually means: a 65%-seeded, up-to-100%-on-error swap rate, not a subtle AI-difficulty knob).

`admin-panel/src/pages/Bots.tsx` also renders and saves against the same `game_configs` rows (`loadConfigs`/`saveGameConfig`), as a secondary, narrower panel focused on the bot-fill fields — it doesn't add any additional reach into this engine beyond what `GameConfig.tsx` already provides.

`admin-panel/src/pages/games/TeenPatti.tsx` is a read-only room browser (`GET /game-rooms` filtered client-side to `game_type = 'teen_patti'`) — it has no `variation` column or control, because table variation (classic/AK47/No-Limit/Muflis/Joker) is chosen entirely client-side at matchmaking time (`mobile/lib/features/games/teen_patti/lobby_page.dart`, five separate lobby entry points), never by admin config — there is no way to enable/disable a specific variant server-side short of removing its lobby entry point from the mobile build.

## DDA win-rate target: two admin UI surfaces, neither actually controls it

This is the most consequential real-money lever in this engine (`backend.md`'s DDA section), and admin-panel control over it is effectively fictional in two different ways:

1. **`admin-panel/src/components/AI/MLConfigPanel.tsx`** ("Bot Settings" card, under AI Control Center) has a "Max Bot Win Rate (%)" slider (`maxWinRate`, tooltip: "Cap bot win rate at X% (fair play: 48-52%)") plus `decisionTreeDepth`/`aggressionLevel`/`difficulty`/`enabled`. Saving posts the whole `MLConfig` object to `POST /api/admin/ml/config` (`services/admin-service/src/ml-routes.ts:60-75`), which writes it to Redis (`ml:config`, 24h TTL) and `admin_config` (Postgres), then publishes `ml:config:change` on Redis pub/sub. **Nothing in the codebase subscribes to `botSettings`.** The only subscriber to `ml:config:change` is `risk-service` (`services/risk-service/src/index.ts:280-292`), and it only reads `config.fraudDetection` — `botSettings`, `churnPrediction`, and `rtpOptimizer` are persisted and published but have zero consumers anywhere. An admin moving this slider believes they are capping bot win rate; nothing enforces that belief.
2. **`admin-panel/src/components/AI/BotLearningSection.tsx`** (also under AI Control Center, embedded in `MLConfigPanel`) is the one UI that *does* read and write the real `bot_profiles` table this engine queries — via `GET/PATCH /api/admin/bots/profiles(/:gameType/:difficulty)` (`services/admin-service/src/bot-learning-routes.ts`) → `bot-learning-service`'s `ProfileBuilder.overrideProfile()` (`services/bot-learning-service/src/profile-builder.ts:260-277`). But its "Override" form only submits `fold_probability`, `call_probability`, and `avg_decision_delay_ms` (`BotLearningSection.tsx:96-100`) — **`win_rate_target` is never sent**, even though `overrideProfile`'s own allow-list explicitly includes it (`profile-builder.ts:261-262`), and the card's `<Statistic>` tiles don't even display the current `win_rate_target` value (only Fold/Call/Raise/Delay/Aggression). The one field this engine's DDA logic actually queries (`SELECT win_rate_target FROM bot_profiles ...`, `main.go:359`) is invisible and unreachable from this form.

The only thing that does change `win_rate_target` in practice is `bot-learning-service`'s nightly automatic rebuild (`ProfileBuilder.rebuildForGame`, `bot_learning_config.rebuild_hour`, default `02:00` per `infra/db/migrations/016_bot_learning.sql`), which is triggerable on demand from `BotLearningSection`'s "Rebuild Now" button — but that recomputes `win_rate_target` **from the observed win rate of real players in that difficulty's profit percentile** (`profile-builder.ts:113-167`; `win_rate_target: Math.round(avgWinRate * 10) / 10`), not from any admin-specified target number. So even the one working control surface only lets an admin adjust the *inputs* to that computation (percentile cutoffs, lookback window, minimum sample size, via the "Schedule & Sampling Config" form) — never the resulting `win_rate_target` directly. See `docs/Bugs/teen-patti-dda-admin-control-gap.md`.

## Live room state and force actions (via game-gateway, not this engine directly)

`admin-service`'s `GET /api/admin/game-rooms/:id/live-state` reads this engine's `tp:game:<roomId>` Redis key **directly**, bypassing both `game-gateway` and this engine's own HTTP surface entirely — it's the one place in the admin stack that can show every seat's actual cards mid-hand, by design, for a "Live Spectator" view. `force-action`/`kick`/`terminate` proxy through `game-gateway`'s internal endpoints, which for `force-action` replay a synthetic call into this engine's own `/action` handler (`docs/backend-services/game-gateway/backend.md`). The frontend for all of this — `admin-panel/src/pages/GameRooms.tsx` — is fully built but **not wired into routing or the nav menu** (already filed: `docs/Bugs/orphaned-admin-pages.md`); see `docs/backend-services/game-gateway/admin.md` for the full breakdown of what it would show if routed. Nothing about that gap is specific to this engine, so it isn't re-filed here.

## What's missing

- No admin visibility into DDA swaps as they happen — the only record is a `log.Printf("[DDAS] ...")` server log line (`main.go:411-414`), not a database row, not an admin-panel feed, not even something `monitor-emitter.ts` forwards to `monitoring-service`.
- No admin visibility into how often the `hard`-fallback-to-100% path (`docs/Bugs/teen-patti-dda-hard-fallback-100-percent.md`) is actually being hit in production — it would show up only as an unusually bot-favorable run of `hard`-difficulty hands, with nothing in any admin view pointing back to the cause.
- No per-variant (AK47/Muflis/Joker) enable/disable switch anywhere in the admin panel — variant availability is purely a function of what lobby entry points ship in the current mobile build.
