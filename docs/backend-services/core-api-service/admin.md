# core-api-service — Admin-panel touchpoints

**The admin panel never calls `core-api-service` directly.** A full search of `admin-panel/src` for the public path prefixes this service owns (`/api/auth/`, `/api/users/`, `/api/leaderboard/`, `/api/notifications/`, `/api/support/`, `/api/betting/`) turns up zero matches. Every admin-panel page goes through `admin-service` (port 3008), which either re-implements the logic against the same Postgres tables directly, or server-to-server proxies specific actions into this service's `/internal/*` routes using the shared `x-internal-key` header. This means RBAC for anything touching this service's data is enforced entirely in `admin-service`'s route definitions (`requireRole(...)` — see `services/admin-service/src/index.ts`), not here; this service's `/internal/*` routes only check the shared internal key, not an admin role.

## Betting management — `admin-panel/src/pages/BettingManagement.tsx`

Calls `admin-service`'s `/api/admin/betting/*`, which proxies write actions to this service's `/internal/*` routes via a `callBetting()` helper (`services/admin-service/src/index.ts:1462`). Role gates on the admin-service side: `requireRole('finance')` for declaring/creating/settling (matka declare, lottery create/draw, cricket match/market/settle, session create/settle, fantasy players/leagues); `requireRole('support')` for the read-only cricapi sync actions (scores update, sync-api, sync-countries, sync-squad) and score updates. Reads (`GET /api/admin/betting/{matka/draws,lottery/draws,cricket/matches,cricket/fantasy/players}`) query Postgres directly from `admin-service`, bypassing this service entirely — only the write/settlement actions round-trip through `core-api-service`.

**This proxy path was broken until fixed 2026-07-28**: `services/admin-service/.env` (and `.env.example`) used to set `BETTING_SERVICE_URL=http://localhost:3012`, the old standalone `betting-service`'s pre-consolidation port. Nothing listens on 3012 — `betting-service` is archived (`archive_microservices/betting-service`, not on the PM2 process list), and this service's betting plugin runs on port 3001. Every admin betting write action (declare a Matka result, create/draw a lottery, create/settle a cricket market or session, register fantasy players/leagues, trigger a cricket API sync) threw on the `fetch()` inside `callBetting()` and 500'd. Both the `.env`/`.env.example` values and the in-code fallback (`services/admin-service/src/index.ts`) now correctly point at `http://localhost:3001`/`http://127.0.0.1:3001`. There is also no admin-panel UI for creating `cricket_fantasy_players`/`cricket_fantasy_leagues` (`BettingManagement.tsx` has no `fantasy`-prefixed call at all, despite the backend route existing) and no UI trigger for the `sync-series`/`import-series-matches` admin-service routes, which in turn call two `core-api-service` routes (`/internal/cricket/sync-series`, `/internal/cricket/import-series-matches`) that don't exist in `betting.ts` — see `docs/backend-services/core-api-service/backend.md`.

## Notifications — `admin-panel/src/pages/Notifications.tsx`

`POST /api/admin/notifications/{send,broadcast}` (`requireRole('support')`) proxy straight through to this service's `POST /internal/notifications/{send,broadcast}`. Same dead-port problem as betting, also fixed 2026-07-28: `admin-service/.env` used to set `NOTIFICATION_SERVICE_URL=http://localhost:3007`, overriding the correct in-code fallback (`http://127.0.0.1:3001`) with a port nothing listens on; now corrected to `http://localhost:3001`. Unlike the betting proxy, these two admin-service routes `await fetch(...)` and `await res.json()` with **no try/catch**, so a broken connection would have surfaced as a 500 to the admin UI rather than failing silently — this class of unguarded-fetch risk remains if the URL is ever misconfigured again. Several *other* admin-service actions also fire a best-effort push through `NOTIFICATION_URL` but wrap the call in `.catch(() => null)` — KYC approve/reject (`PATCH /api/admin/users/:id/kyc`), withdrawal status changes, and deposit reconciliation (`PATCH /api/admin/finance/deposits/:id`) — these fail silently (no error surfaced to the admin) if the notification call ever fails for any reason, independent of the port fix.

## Users / bank details / daily bonus

`admin-service` has its own, properly-secured bank-details routes (`GET /api/admin/bank-details` — any authenticated admin; `PATCH /api/admin/bank-details/:userId/verify` — `requireRole('finance')`) that query the same `bank_details` table `core-api-service`'s profile plugin writes to, but do not call this service. `core-api-service` used to also carry its own dead, unauthenticated `/admin/bank-details` leftover routes (`users.ts`) — never used by the admin panel — removed 2026-07-29. Daily-bonus config (`GET`/`PUT /bonus/login-config`, `requireRole('finance')` on the write) and stats live entirely in `admin-service`, reading/writing `login_bonus_config` and `bonuses`/`user_login_streaks` directly — no proxy to this service either, even though the player-facing claim flow (`POST /users/daily-bonus/claim`, this service) reads the same `login_bonus_config` table. Both services independently query the same tables rather than one calling the other; there's no `/internal/*` route in `core-api-service` for daily-bonus config.

## Leaderboard, support, auth — no admin-panel-specific behavior beyond what's already documented

- Leaderboard: no admin-panel page manages it; see `docs/app/leaderboard/admin.md` (if present) or `docs/app/leaderboard/backend.md` — there is no reward payout to intervene on.
- Support: see `docs/admin-panel/support/backend.md` for the admin side of ticket handling (the `is_internal` message flag this service's routes filter out).
- Auth: see `docs/app/auth/admin.md` — the admin panel's only leverage over player auth is `users.status`, enforced by `core-api-service`'s own login route, not by anything admin-service calls into this service for.
